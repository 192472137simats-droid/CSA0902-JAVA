# Q4 – Choosing a Map for a Pharmacy Inventory

## Overview
This task investigates the optimal `Map` implementation (`HashMap`, `TreeMap`, or `LinkedHashMap`) for a Hospital Pharmacy stock lookup and evening reporting system across 500, 5,000, and 50,000 medicine catalog sizes.

## Files
- `PharmacyInventory.java`: Benchmark suite testing 100,000 lookups, code-order report generation, and insertion-order report generation.
- `expected_output.txt`: Measured execution times and comparative results.

## Compilation and Execution
```bash
javac PharmacyInventory.java
java PharmacyInventory
```

## Summary of Findings & Deployment Decision
- **Lookup Performance**:
  - `HashMap` and `LinkedHashMap` provide average $O(1)$ lookup (~2.9 ms for 100,000 lookups at 50,000 medicines).
  - `TreeMap` requires $O(\log n)$ tree-node traversals (~57.3 ms for 100,000 lookups).
- **Report Generation**:
  - Code-order report: Naturally generated by `TreeMap` in $O(n)$ time via in-order tree traversal.
  - Insertion-order report: Naturally generated by `LinkedHashMap` in $O(n)$ time via its internal doubly-linked bucket list (0.6 ms).
  - `HashMap` produces an arbitrary bucket order and requires external sorting or indexing for both reports.
- **Recommended Deployment**:
  - **`LinkedHashMap`** is recommended for production. Since frequent lookups occur continuously throughout the working day, the $O(1)$ lookup time provides immediate response times (< 0.0001 ms/query). In the evening, the insertion-order report is free ($O(n)$), and the code-order report is easily generated in 25 ms by a single $O(n \log n)$ sort of key references.
- **Why `Hashtable` Is Not Preferred**:
  - Every method in legacy `Hashtable` is synchronized with a single coarse-grained object monitor lock, destroying throughput in concurrent environments. In addition, it prohibits `null` keys/values and has been superseded by `ConcurrentHashMap` and `HashMap`.
